\section{Introducción}

Se detalla la justificación organizativa de los archivos, los paradigmas de modularidad aplicados y los principios de separación de responsabilidades que permiten que el código sea escalable y fácil de mantener.

\section{Estructura de directorios}
La base de código fuente se organiza bajo el paradigma de \textbf{\textit{Monorepo}}~\cite{monorepo} (repositorio monolítico). Este patrón centraliza el cliente web y el servidor dentro del mismo control de versiones, facilitando la integración continua (CI/CD), la orquestación conjunta mediante Docker y la coherencia estructural.

\subsection{Arquitectura de control de calidad (Colocation Principle)}\label{sec:colocation}
Un elemento clave en la arquitectura técnica de AgroSkopos es la estructuración organizativa de los archivos de pruebas. Los archivos de pruebas unitarias no se almacenan aislados en una única carpeta global (como \texttt{tests/}) en la raíz. 

En su lugar, el proyecto adopta el \textbf{Principio de \textit{Colocation}~\cite{colocation}}: tanto en el servidor como en el cliente web, las carpetas \texttt{\_\_tests\_\_} o los archivos terminados en \texttt{.test.js} se declaran \textbf{exactamente en el mismo directorio} que el código fuente que evalúan (ej. \texttt{DataPage.test.jsx} vive junto a \texttt{DataPage.jsx}). Este enfoque presenta dos ventajas vitales:
\begin{enumerate}
    \item \textbf{Mantenibilidad:} Un desarrollador localiza al instante los test de un archivo, lo que fomenta el \textit{Test-Driven Development} (TDD).
    \item \textbf{Refactorización:} Al mover un componente React o un servicio de Node.js a otro directorio, su test se mueve con él de forma natural, evitando que se rompan las rutas de importación relativas.
\end{enumerate}

La única excepción a este principio se aplica a las \textbf{pruebas \textit{End-to-End} (E2E)}. Dado que estas validan el sistema web en su conjunto interactuando con toda la pila tecnológica (levantando bases de datos con \textit{Testcontainers}), residen en una estructura separada.

\section{Manual del programador}

Esta sección tiene como propósito servir de guía técnica para futuros desarrolladores que necesiten mantener, extender o depurar el sistema AgroSkopos. Se documentan aquí los patrones de arquitectura aplicados, el ciclo de vida de los datos y las convenciones de programación adoptadas, de manera complementaria a los diagramas arquitectónicos expuestos en el Anexo C.

\subsection{Calidad estática del código}
El repositorio emplea herramientas automatizadas para garantizar un estilo de código homogéneo y libre de defectos lógicos. En los proyectos de cliente y servidor se utilizan \textbf{ESLint} para la validación estática. Además, todo el código subido al repositorio es analizado de forma continua por \textbf{SonarCloud~\cite{sonarqube}} (según lo descrito en la configuración CI de \textit{GitHub Actions}), que mide la deuda técnica, las vulnerabilidades y la cobertura de pruebas. Cualquier nuevo desarrollo debe adherirse a estas normativas para superar las barreras de integración. Adicionalmente, es un requisito estricto mantener y ampliar la batería de pruebas (unitarias y E2E) a medida que se escribe nuevo código o se modifican funcionalidades existentes, asegurando que la cobertura no disminuya y protegiendo el sistema continuamente contra regresiones.

\subsection{El flujo de una petición en el \textit{Backend} (API REST)}
El servidor, construido sobre Node.js y Express~\cite{express}, aísla la lógica en capas. El flujo de una solicitud HTTP típica (por ejemplo, crear una misión) es el siguiente:
\begin{enumerate}
    \item \textbf{Capa de Rutas (\texttt{routes/}):} Recibe la petición HTTP y la delega a los interceptores correspondientes.
    \item \textbf{Capa de Validación Estricta (\texttt{schemas/}):} Antes de invocar a la lógica de negocio, se validan los parámetros de entrada utilizando la librería \textbf{Zod}~\cite{zod} (ej. \texttt{missionSchema.js}, \texttt{robotSchema.js}). Si la estructura o los tipos de datos no coinciden con los esperados, la solicitud es interceptada y rechazada automáticamente, impidiendo posibles inyecciones o corrupciones en la base de datos.
    \item \textbf{Capa de Controlador (\texttt{controllers/}):} Extrae la información ya formateada y limpia, para pasársela a los servicios.
    \item \textbf{Capa de Servicios (\texttt{services/}):} Ejecuta la lógica empresarial pura y realiza las transacciones necesarias empleando \textbf{Prisma ORM}~\cite{prisma} contra la base de datos PostgreSQL~\cite{postgresql}.
\end{enumerate}

\subsection{Manejo de Errores (\textit{Error Handler} Global)}
El sistema implementa un interceptor centralizado (\texttt{errorHandler.js}) por el que pasan todas las excepciones asíncronas antes de ser devueltas al cliente. Este \textit{middleware} filtra y traduce los errores técnicos a formatos limpios y seguros:
\begin{itemize}
    \item \textbf{Mapeo de base de datos:} Traduce códigos de error nativos de PostgreSQL (ej. \texttt{23505} para duplicados o \texttt{23503} para violaciones de claves foráneas) a mensajes legibles.
    \item \textbf{Errores de Validación:} Desglosa los fallos capturados por \textbf{Zod} en un array estructurado (indicando el campo y la clave de traducción del error) para que el \textit{frontend} pueda mostrar validaciones campo por campo en los formularios.
    \item \textbf{Excepciones Estructuradas:} A través de la clase personalizada \texttt{AppError}, todos los errores operacionales incluyen un código HTTP semántico (400, 401, 404, 500) y una clave interna constante (ej. \texttt{VALIDATION\_ERROR}), facilitando el manejo programático en el cliente sin depender del idioma del mensaje.
\end{itemize}

\subsection{Comunicaciones asíncronas y motor de simulación (\textit{Simulator})}
Uno de los componentes centrales y más complejos del servidor es el \textbf{Motor de Simulación} (\texttt{simulator/}). Este motor emula en tiempo real la física y las operaciones del robot agrícola, y ha sido arquitectónicamente refactorizado en un ecosistema altamente modular compuesto por:
\begin{itemize}
    \item \textbf{Bucle Principal y Estado (\texttt{index.js} y \texttt{state.js}):} El núcleo del simulador mantiene en memoria el estado unificado del robot y ejecuta un bucle infinito de ciclos de reloj (\textit{ticks}) en segundo plano.
    \item \textbf{Sistemas Lógicos (\texttt{systems/}):} La complejidad se ha desacoplado en motores independientes que actúan sobre el estado global en cada ciclo:
    \begin{itemize}
        \item \textbf{\texttt{movement.js}:} Calcula la cinemática, genera rutas de barrido iterando mallas de polígonos geográficos (\texttt{@turf/turf}) y resuelve el \textit{pathfinding} autónomo.
        \item \textbf{\texttt{energy.js}:} Evalúa el consumo dinámico frente a la velocidad, inyecta la ganancia de los paneles solares y determina el umbral crítico para forzar el retorno automático a la base (\textit{RTL}).
        \item \textbf{\texttt{agronomy.js}:} Simula los parámetros edafológicos del suelo (Humedad, pH, NPK) con inyección de variables ambientales lógicas.
    \end{itemize}
\end{itemize}
Debido a la altísima frecuencia de muestreo, los datos calculados no viajan mediante protocolo HTTP tradicional. Se emplea un canal bidireccional asíncrono con \textbf{WebSockets} (\texttt{websockets/socketHandler.js}), emitiendo paquetes de telemetría constante a todos los clientes web conectados.

\subsection{Gestión de Estado (Carpeta \texttt{store/})}
Para evitar bloqueos y cuellos de botella en la interfaz interactiva de React frente a la ráfaga de datos en tiempo real, AgroSkopos abandona soluciones monolíticas y delega la responsabilidad a un modelo segregado ultrarrápido:
\begin{itemize}
    \item \textbf{Estado Global mediante Zustand (\texttt{store/}):} Toda la memoria compartida de la aplicación se centraliza en la carpeta \texttt{store/}. Aquí se instancian repositorios (\textit{stores}) atómicos y directos (ej. \texttt{robotStore.js} para telemetría, \texttt{authStore.js} para sesiones de usuario). Zustand emplea actualizaciones selectivas, permitiendo inyectar coordenadas GPS masivas al mapa sin forzar un pesado re-renderizado en cascada del DOM subyacente.
    \item \textbf{Estado Local y Caché:} Se reserva la memoria interna reactiva (\texttt{useState}) únicamente para variables efímeras visuales (ej. aperturas de modales o textos de formularios), separando limpiamente la lógica técnica del dibujo web.
\end{itemize}

\subsection{Guía para extender la interfaz (Feature-Sliced Design~\cite{featuresliced})}
Si un desarrollador necesita escalar el proyecto y agregar un nuevo módulo interactivo, debe adherirse estrictamente a la topología de carpetas impuesta. Para añadir una nueva funcionalidad (por ejemplo, un visor geológico), el flujo de trabajo es el siguiente:
\begin{enumerate}
    \item \textbf{Lógica de Dominio (\texttt{features/}):} Aislar la inteligencia creando una carpeta en \texttt{features/geology/}. Dentro de este directorio, el programador creará sus propias subcarpetas (\texttt{components/}, \texttt{utils/}) para empaquetar de forma cohesiva los elementos visuales y métodos que son exclusivos de esa funcionalidad.
    \item \textbf{Lógica Reactiva Global (\texttt{hooks/}):} Si el módulo requiere ciclos de vida complejos o peticiones recurrentes a la API que trascienden el dominio aislado (ej. un gancho para sondear APIs meteorológicas), deberá abstraerse como un \textit{Custom Hook} dentro de la carpeta global \texttt{hooks/}.
    \item \textbf{Variables Globales (\texttt{store/}):} Si este nuevo bloque necesita compartir datos cruciales que otras partes de la app consumirán, añadirá o creará un repositorio dedicado en la carpeta \texttt{store/} (Zustand).
    \item \textbf{Ensamblaje Arquitectónico (\texttt{pages/} y \texttt{App.jsx}):} Exponer públicamente los bloques construidos en \texttt{features/} e integrarlos visualmente fabricando una vista global dentro del directorio \texttt{pages/} (ej. \texttt{pages/Geology/GeologyPage.jsx}). Por último, se registrará esta página maestra en el árbol de rutas de \texttt{App.jsx}.
\end{enumerate}

\section{Despliegue, instalación y ejecución del proyecto}

AgroSkopos ha sido diseñado con una arquitectura agnóstica de plataforma, lo que permite que su despliegue y ejecución sean idénticos tanto en entornos locales de desarrollo como en infraestructuras productivas en la nube. Todo el ecosistema de dependencias, desde los motores de Node.js hasta la configuración de base de datos, ha sido abstraído mediante la tecnología de contenerización de \textbf{Docker}.

\subsection{Despliegue en Entorno de Producción}
Actualmente, el sistema se encuentra desplegado en un entorno productivo híbrido para maximizar su disponibilidad:
\begin{itemize}
    \item \textbf{Capa de Presentación (\textit{Frontend}):} Desplegado mediante infraestructura \textit{Serverless} en Vercel, sirviendo los archivos estáticos compilados a través de su red global de entrega de contenido (CDN) de forma segura bajo protocolo HTTPS.
    \item \textbf{Capa de Lógica y Datos (\textit{Backend} y BBDD):} Alojado en una máquina virtual de Linux en Microsoft Azure, en la cual se ejecuta el orquestador \texttt{docker-compose} para mantener activos los contenedores de PostgreSQL, Redis y la API REST con Node.js de forma ininterrumpida.
\end{itemize}

\subsection{Instalación y Configuración Local}
Para el departamento de ingeniería, replicar el ecosistema de producción en un ordenador local de desarrollo es un proceso trivial y estandarizado.

\textbf{Requisitos Previos:}
El ordenador anfitrión debe tener instalados únicamente dos programas:
\begin{enumerate}
    \item \textbf{Git:} Para clonar el código fuente y el control de versiones.
    \item \textbf{Docker Desktop (o Docker Engine):} Que incluye el motor de contenedores y la utilidad \texttt{docker-compose}.
\end{enumerate}
No es necesario instalar de forma nativa Node.js, NPM, PostgreSQL ni Redis en la máquina local, ya que todas estas tecnologías vendrán incrustadas y preconfiguradas dentro de sus respectivos contenedores.

\textbf{Proceso de Despliegue Paso a Paso:}
\begin{enumerate}
    \item \textbf{Obtención del código:} 
    El programador debe abrir una terminal y clonar el repositorio principal de la empresa:
    \begin{verbatim}
git clone https://github.com/AndresVeraCachoo/aplicacion-robot-agricola.git
cd aplicacion-robot-agricola
    \end{verbatim}
    
    \item \textbf{Configuración de Entorno:}
    El proyecto requiere de un archivo de configuración de variables secretas. En la raíz del proyecto, se provee un archivo de plantilla estandarizado que contiene todos los valores predeterminados para desarrollo (contraseñas de base de datos, configuraciones de puertos, etc.). El operario simplemente debe duplicar este archivo:
    \begin{verbatim}
cp .env.example .env
    \end{verbatim}
    Estos valores por defecto son completamente válidos y seguros para operar y testear la aplicación de forma aislada en \texttt{localhost}.

    \item \textbf{Orquestación y Compilación Simultánea:}
    Al ejecutar un único comando en la terminal, el sistema descarga las imágenes oficiales, instala las dependencias del \textit{frontend} y \textit{backend}, compila el código y levanta la red virtual que conecta la base de datos con los servidores:
    \begin{verbatim}
docker-compose up --build -d
    \end{verbatim}
    El parámetro \texttt{--build} asegura que el código fuente actual del repositorio se inyecte en imágenes frescas, mientras que el parámetro \texttt{-d} (\textit{Detached}) permite que los contenedores se ejecuten de fondo, liberando la consola para seguir trabajando.
    
    \item \textbf{Inicialización Automática de Datos (\textit{Seeding}):}
    En el primer arranque, la base de datos ejecuta un \textit{script} automático (\texttt{database/init.sql}) que crea las tablas e inserta datos iniciales (misiones de prueba, datos agronómicos y el usuario \texttt{admin}), permitiendo realizar pruebas funcionales de inmediato.
\end{enumerate}

\subsection{Accesos y Puntos de Entrada}
Una vez que el comando \texttt{docker-compose} finalice exitosamente, los cuatro contenedores estarán vivos y mapeados a los puertos locales del desarrollador. Se podrá interactuar con el ecosistema a través de las siguientes URLs en cualquier navegador estándar:

\begin{itemize}
    \item \textbf{Interfaz Web del Usuario:} \texttt{http://localhost:8080}
    \item \textbf{API \textit{Backend} Base:} \texttt{http://localhost:3001/api}
    \item \textbf{Documentación Interactiva (Swagger):} \texttt{http://localhost:3001/api-docs}. Este portal avanzado permite al desarrollador leer la especificación de todos los \textit{endpoints} disponibles y lanzar peticiones HTTP reales (como crear un usuario o borrar una misión) directamente contra su servidor local para verificar su funcionamiento, evitando la necesidad de instalar clientes externos como Postman o Insomnia.
\end{itemize}
\section{Pruebas del sistema}

La calidad del \textit{software} (QA) en AgroSkopos se asegura mediante pruebas automatizadas en múltiples capas, abarcando la lógica del \textit{backend}, el \textit{frontend} y la infraestructura. Todas estas pruebas se ejecutan localmente y de forma automatizada en Integración Continua (CI).

\subsection{Pruebas del Cliente Web (\textit{Frontend})}
Para el entorno interactivo en React, se emplea \textbf{Vitest}~\cite{vitest} combinado con \textbf{React \textit{Testing} Library} y \texttt{jest-dom}. Vitest actúa como empaquetador (\textit{bundler}) y motor de pruebas, facilitando la integración respecto a Jest en navegadores modernos.
Las pruebas se centran en el comportamiento observable por el usuario. Se validan:
\begin{itemize}
    \item \textbf{Componentes UI:} Renderizado correcto, manejo de eventos (\textit{clicks}, \textit{inputs}) utilizando \texttt{@testing-library/user-event} y flujos de modales.
    \item \textbf{Lógica de estado y red:} Pruebas sobre \textit{stores} globales (ej. \texttt{authStore.test.js}) y servicios de red o utilidades cliente.
\end{itemize}

Los comandos disponibles (ejecutables desde la raíz del monorepo) incluyen:
\begin{itemize}
    \item \texttt{npm run test:unit}: Ejecuta la batería de pruebas unitarias en todo el monorepo (incluyendo el \textit{frontend}).
    \item \texttt{npm run test:unit:cov}: Ejecuta las pruebas e instrumenta el código para generar un informe completo de cobertura.
\end{itemize}

\subsection{Pruebas del Servidor (\textit{Backend})}
En el lado del servidor, se emplea \textbf{Jest}~\cite{jest} configurado para operar nativamente con módulos ES. Se distinguen tres niveles de evaluación crítica:

\subsubsection{Pruebas Unitarias}
Siguen el Principio de \textit{Colocation} detallado en la sección \ref{sec:colocation}. Evalúan de forma aislada componentes lógicos individuales como controladores, \textit{middlewares} y esquemas de validación, simulando (\textit{mocking})~\cite{mocking} las dependencias externas y accesos a la base de datos.

\subsubsection{Pruebas \textit{End-to-End} (E2E)~\cite{e2e}}
Dado que el servidor interactúa intensivamente con una base de datos PostgreSQL y una caché Redis~\cite{redis}, las pruebas E2E (alojadas en la carpeta \texttt{app/server/tests/}) validan los flujos completos empleando \textbf{Supertest}~\cite{supertest}.
Para lograr un entorno determinista, se utiliza la herramienta \textbf{Testcontainers}. Esta librería levanta dinámicamente contenedores Docker efímeros de PostgreSQL y Redis antes de la ejecución, aplica las migraciones y los destruye al finalizar.
\begin{itemize}
    \item Ejecución: \texttt{npm run test:e2e}
    \item Ejecución con cobertura: \texttt{npm run test:e2e:cov}
\end{itemize}

\subsubsection{Pruebas de Carga y Estrés (k6)}
Para garantizar la estabilidad del servidor en producción frente a picos masivos de telemetría provenientes del campo, el proyecto integra una suite de pruebas de rendimiento escrita en \textbf{k6}. Se definen cuatro escenarios fundamentales que atacan directamente los \textit{endpoints} más exigentes de la API:
\begin{itemize}
    \item \textbf{Load (Carga nominal):} Evalúa el rendimiento bajo un volumen de tráfico sostenido normal (\texttt{npm run test:k6:load}).
    \item \textbf{Stress (Límite de ruptura):} Incrementa gradualmente los usuarios concurrentes para identificar en qué punto el servidor empieza a denegar conexiones (\texttt{npm run test:k6:stress}).
    \item \textbf{Spike (Pico repentino):} Inyecta un torrente masivo de tráfico instantáneo para comprobar cómo el servidor reacciona y se recupera (\texttt{npm run test:k6:spike}).
    \item \textbf{Soak (Carga prolongada):} Mantiene una carga media durante horas para detectar posibles fugas de memoria o cuellos de botella en la conexión a la base de datos (\texttt{npm run test:k6:soak}).
\end{itemize}
El desarrollador puede ejecutar todos los escenarios en secuencia navegando al directorio del servidor y lanzando el comando: \texttt{node tests/config/run-k6.js all}.

\subsection{Cobertura de Código (\textit{Coverage}) y Consolidación}
La métrica de cobertura certifica qué porcentaje del código fuente (Líneas, Ramas, Funciones y Declaraciones) ha sido ejecutado por las pruebas.

AgroSkopos, al ser un \textit{monorepo}, genera los informes de cobertura de forma local y segregada. Tras ejecutar cualquier comando global de cobertura (por ejemplo \texttt{npm run test:cov}), el sistema dispara automáticamente de forma secuencial el \textit{script} \texttt{merge-coverage.js}. Este \textit{script} tiene la responsabilidad de recolectar todos los archivos \texttt{lcov.info} aislados generados por el cliente, el servidor unitario y el servidor E2E, fusionándolos en un único reporte maestro en el directorio raíz para enviarlo a herramientas externas como SonarCloud~\cite{sonarqube}.

Aunque los resúmenes de cobertura se imprimen textualmente de forma condensada en la consola del desarrollador, los análisis exhaustivos y visuales se pueden revisar navegando línea por línea mediante los archivos HTML generados automáticamente en las siguientes rutas del proyecto (solo hace falta abrir el archivo \texttt{index.html} en cualquier navegador web):
\begin{itemize}
    \item \textbf{Frontend (Unitarias):} \texttt{app/client/coverage/index.html}
    \item \textbf{Backend (Unitarias):} \texttt{app/server/coverage/unit/index.html}
    \item \textbf{Backend (E2E):} \texttt{app/server/coverage/e2e/index.html}
\end{itemize}

\subsection{Automatización en Integración Continua (CI)}
Adicionalmente a la ejecución manual, el proyecto cuenta con un flujo de trabajo configurado en \textbf{GitHub Actions}. Según se define en el archivo \texttt{.github/workflows/ci-sonarcloud.yml}, cada \textit{push} o \textit{Pull Request} hacia la rama principal provoca que una máquina virtual en la nube instale el proyecto y ejecute de forma desatendida las baterías unitarias y E2E. Si alguna prueba falla, el código es rechazado de inmediato. Si pasan con éxito, los archivos de cobertura fusionados se envían automáticamente a la plataforma \textbf{SonarCloud~\cite{sonarqube}} para auditar rigurosamente la deuda técnica y la seguridad del nuevo código.
