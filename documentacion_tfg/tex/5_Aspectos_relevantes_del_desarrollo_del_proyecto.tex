\capitulo{5}{Aspectos relevantes del desarrollo del proyecto}

En este capítulo se describe el ciclo de vida completo del proyecto AgroSkopos, abordando desde su concepción inicial y planificación metodológica, hasta las fases de implementación técnica y validación. 

\section{Motivación del proyecto}

El origen de este Trabajo de Fin de Grado surge del interés por aplicar y consolidar los conocimientos adquiridos en la titulación en un entorno práctico multidisciplinar. La motivación principal fue el diseño de una plataforma de telemetría y control agrícola capaz de integrarse de forma colaborativa con otro Trabajo de Fin de Grado perteneciente a la rama de Ingeniería Electrónica. Mientras que dicho proyecto abordaba el diseño, ensamblaje y la programación a bajo nivel del chasis físico de un robot agrícola, el presente trabajo asumió el reto de desarrollar de forma íntegra toda la capa de \textit{software} de alto nivel. 

Esto incluía la creación de la infraestructura de comunicaciones, la persistencia de datos y la interfaz de usuario que permitiría gobernar dicho vehículo de forma remota. Esta propuesta representó un desafío técnico sumamente enriquecedor, al permitir la convergencia metodológica entre el desarrollo de aplicaciones web modernas orientadas a la baja latencia y la interacción directa con el \textit{hardware} en el ámbito del Internet de las Cosas (IoT).

\section{Inicio del proyecto y evolución del alcance}

En la fase inicial de toma de requisitos, planteada a principio de septiembre, el alcance del proyecto era considerablemente más reducido y lineal. El objetivo original consistía en desarrollar una aplicación funcional que cubriera la gestión básica de usuarios y permitiría visualizar la telemetría del robot en tiempo real. En cuanto al control, únicamente se contemplaba una navegación rudimentaria mediante el envío de coordenadas individuales basadas en los clics del operador sobre un mapa, complementado con tablas y gráficas estáticas para el análisis de los datos.

Sin embargo, durante el transcurso del curso académico, el proyecto experimentó una reestructuración forzosa. Diversos problemas técnicos, logísticos y de suministro impidieron que el proyecto de Ingeniería Electrónica pudiera finalizar la construcción del robot físico a tiempo. Esta eventualidad imposibilitó la fase de integración de \textit{hardware} que estaba prevista inicialmente.

Lejos de suponer un bloqueo, este contratiempo impulsó una ambiciosa evolución orgánica del \textit{software}. Para poder validar la arquitectura orientada a eventos y la recepción de telemetría, el \textbf{motor de simulación interno} (que inicialmente se había concebido como un simple \textit{script} de pruebas temporales) se reescribió por completo y se dotó de algoritmos cinemáticos avanzados. Al no requerir la inversión de tiempo en la integración física, el esfuerzo de desarrollo se redirigió hacia la ampliación masiva de las funcionalidades de la plataforma, convirtiendo lo que iba a ser un simple visor de datos en un producto tecnológico integral mucho más completo.

De este modo, se incorporó un complejo sistema de \textbf{misiones autónomas y planificación de rutas}, delimitación virtual del terreno (geocercas), soporte multilenguaje (i18n), personalización de la interfaz (modo oscuro) y la migración arquitectónica hacia una \textbf{Aplicación Web Progresiva (PWA)}.

\section{Adquisición de conceptos técnicos}

El desarrollo de una aplicación con requerimientos de telemetría, simulación cinemática y mapas interactivos en tiempo real supuso un desafío técnico significativo, exigiendo un periodo intensivo de capacitación tecnológica previo a la fase de codificación. Puesto que el \textit{stack} tecnológico empleado (PERN: PostgreSQL \cite{postgresql}, Express \cite{express}, React \cite{react} y Node.js \cite{nodejs}) difería notablemente de las tecnologías abordadas con profundidad a lo largo del plan de estudios del grado, el proyecto requirió un firme proceso de investigación y autoaprendizaje.

Esta adquisición de competencias se llevó a cabo en dos etapas diferenciadas:

\begin{itemize}
    \item \textbf{Etapa Inicial (Verano 2025):} El proceso de formación comenzó durante el periodo estival, coincidiendo con las prácticas extracurriculares en empresa. En esta fase se llevó a cabo un estudio autodidacta centrado en los fundamentos del desarrollo web moderno, asimilando la sintaxis y capacidades de JavaScript (ES6+), así como la estructuración y diseño con HTML5 y CSS3. Esta etapa sentó las bases necesarias para abordar la programación orientada a la web con la agilidad requerida.
    \item \textbf{Etapa de Pre-desarrollo (Septiembre - Octubre 2025):} Tras la formalización de los requisitos del proyecto, se estableció un bloque de un mes dedicado de forma exclusiva a la investigación teórica, antes de realizar la primera confirmación de código (\textit{commit}). Durante este tiempo se consolidó el dominio del ecosistema de React \cite{react} y de las tecnologías fundamentales para AgroSkopos:
    \begin{itemize}
        \item \textbf{Paradigma de React y Estado Global:} Se profundizó en el modelo declarativo, el ciclo de vida de los componentes y la gestión avanzada de estados globales mediante \textit{hooks} optimizados como Zustand \cite{zustand}, previendo el alto volumen de datos de telemetría que la aplicación debía manejar.
        \item \textbf{Librerías Geoespaciales (Leaflet):} Sabiendo que el núcleo visual del proyecto iba a ser un visor interactivo de precisión, se realizó un estudio pormenorizado de la API de Leaflet \cite{leaflet}. Se analizaron conceptos cartográficos como las capas de teselas (\textit{tile layers}), las proyecciones de coordenadas y la renderización reactiva de polígonos y marcadores.
    \end{itemize}
\end{itemize}

Esta fase preparatoria resultó crítica para mitigar los riesgos técnicos del proyecto. El tiempo invertido garantizó que, una vez iniciado el desarrollo \textit{frontend}, se ejecutara bajo decisiones de diseño de \textit{software} maduras, limpias y escalables, evitando la deuda técnica temprana.

\section{Planificación}

La planificación del proyecto se estructuró asumiendo la alta incertidumbre derivada de un desarrollo dependiente, en sus inicios, de factores externos (el \textit{hardware}). Como se documentó en el capítulo metodológico, se empleó \textbf{Scrum} junto a la herramienta \textbf{Zube} para orquestar el trabajo en iteraciones o \textit{sprints} de dos semanas.

Esta fragmentación en ciclos de entrega cortos permitió aislar la complejidad y otorgó una gran capacidad de adaptación ante los cambios de alcance. De este modo, se garantizó que el núcleo de la aplicación estuviera siempre consolidado y operativo antes de implementar nuevas capas de lógica de negocio o complejas mecánicas de visualización por encima de él.

El ciclo de desarrollo se dividió transversalmente en las siguientes grandes fases o hitos planificados:
\begin{enumerate}
    \item \textbf{Fase de Análisis y Diseño:} Toma de requisitos iniciales, diseño de la base de datos relacional y elaboración de los prototipos de la interfaz gráfica de usuario.
    \item \textbf{Fase de Desarrollo \textit{Frontend}:} Construcción de la \textit{Single Page Application} (SPA) con React \cite{react}, integración del mapa interactivo con Leaflet \cite{leaflet} y conexión con los servicios del \textit{backend}.
    \item \textbf{Fase de Desarrollo \textit{Backend}:} Implementación del servidor Node.js \cite{nodejs}, despliegue del contenedor PostgreSQL \cite{postgresql}, configuración de la API REST y establecimiento del servidor de WebSockets para la comunicación bidireccional.
    \item \textbf{Fase de Refactorización y Simulación Avanzada:} Hito introducido tras la cancelación de las pruebas físicas. Consistió en el desarrollo del motor de simulación cinemática y la generación dinámica de datos agronómicos para replicar el comportamiento de un entorno real.
    \item \textbf{Fase de Expansión de Funcionalidades:} Implementación de las misiones, algoritmos de navegación (rutas de cobertura y \textit{zigzag}), internacionalización y configuración de la PWA.
    \item \textbf{Fase de Pruebas (\textit{Testing}) y Aseguramiento de la Calidad:} Consolidación de las pruebas unitarias y E2E, y análisis estático con SonarCloud \cite{sonarqube}.
    \item \textbf{Fase de Pruebas de Carga y Despliegue en la Nube:} Pruebas de carga con k6 \cite{k6}, contenedorización final mediante Docker \cite{docker} Compose y orquestación productiva en Vercel \cite{vercel} y Azure \cite{azure}.
\end{enumerate}

\section{Desarrollo del Backend}

La implementación de la lógica del servidor de AgroSkopos fue un proceso iterativo que evolucionó conforme a las crecientes necesidades del sistema, priorizando siempre la estabilidad y la escalabilidad.

\subsection{Arquitectura, Seguridad y Modelado de Datos inicial}
Una vez cimentadas las bases visuales en las primeras semanas de trabajo, el enfoque se trasladó al servidor \textbf{Node.js \cite{nodejs}}. Se abandonaron los datos estáticos migrando el núcleo de almacenamiento a \textbf{PostgreSQL \cite{postgresql}}. En esta fase temprana, el diseño de la persistencia de datos persiguió una filosofía de extrema simplicidad para evitar la sobreingeniería inicial. Originalmente, el sistema operaba únicamente con tres tablas maestras: \textit{Usuarios} (gestión de acceso), \textit{Misiones} (estado de los recorridos del robot) y \textit{Telemetría} (captura de datos masivos). La comunicación con la base de datos se realizaba mediante consultas SQL crudas integradas directamente en el código del servidor.

Paralelamente, se implementaron los pilares de seguridad del sistema. Se integró el cifrado asimétrico de contraseñas mediante \textbf{Bcrypt} y un robusto sistema de autenticación basado en \textbf{\textit{JSON Web Tokens} (JWT)}, complementado con una lógica de Control de Acceso Basado en Roles (RBAC) para proteger las rutas de la API de usuarios no autorizados.

Para mitigar vulnerabilidades críticas como los ataques de secuestro de sesión (\textit{Cross-Site Scripting} o XSS), se diseñó un mecanismo de doble \textit{token} (\textit{AccessToken} de vida corta y \textit{RefreshToken} de vida larga). Estos \textit{tokens} no se inyectan en el \textit{LocalStorage} del navegador (que es vulnerable a la inyección de \textit{scripts}), sino que viajan directamente en \textbf{\textit{Cookies HttpOnly}}. Esto asegura que las credenciales sean totalmente inaccesibles desde el código del cliente y se adjunten de forma automática y transparente en cada petición.

\imagen{./img/apartado_4/flujo_autenticacion.png}{Flujo de Autenticación mediante JWT y Cookies HttpOnly}{0.9}

\subsection{Evolución del ORM y Validación de Datos}
A medida que creció la complejidad de las funcionalidades y aumentaron las tablas y relaciones de la aplicación, se hizo evidente la necesidad de escalar el sistema. Para ello, se integró el motor de persistencia \textbf{Prisma ORM}. Prisma permitió mantener una estructura de datos limpia pero abstrajo por completo la redacción manual de SQL, mitigando el riesgo de inyección de código y delegando al \textit{framework} la generación automática de migraciones.

Aún más importante, Prisma actuó como el pilar fundamental para lograr un \textbf{Tipado Estricto de Extremo a Extremo} (\textit{End-to-End Type Safety}). Al combinar los tipos autogenerados por la base de datos de Prisma con la librería de validación estática \textbf{Zod} en la entrada de las peticiones HTTP, se garantizó que la información fluyera con una integridad estructural matemática, detectando discrepancias mucho antes del tiempo de ejecución.

Además, para unificar las respuestas de fallo (como un \textit{payload} malformado de Zod o un fallo interno del servidor) y evitar que se filtren trazas de pila sensibles en producción, se diseñó un \textbf{\textit{Middleware} de Manejo Global de Errores} que actúa como sumidero final y devuelve errores HTTP estandarizados y limpios al cliente.

\subsection{Integración de Sistemas y Simulación Telemétrica}
Ante la cancelación definitiva de las pruebas con el chasis físico del robot, el desarrollo del servidor pivotó hacia la creación de un \textbf{simulador telemétrico avanzado}. Para soportar el envío masivo de estados robóticos, se sustituyeron las tradicionales peticiones HTTP orientadas a la gestión por una arquitectura de baja latencia impulsada por \textbf{WebSockets} bidireccionales. El servidor de AgroSkopos adoptó entonces el papel de despachador principal (\textit{Broker}), capaz de inyectar variables cinemáticas, niveles de batería y coordenadas GPS sobre la red en milisegundos para actualizar la pantalla de los clientes en estricto tiempo real.

\section{Desarrollo del Frontend}

El cliente web evolucionó desde una sencilla interfaz de visualización estática hasta convertirse en una plataforma de gestión agrícola profundamente interactiva.

\subsection{Cimentación Arquitectónica y Prototipado Visual}
El desarrollo del \textit{software} dio comienzo con la configuración del entorno moderno impulsado por \textbf{React \cite{react}} y \textbf{Vite \cite{vite}}. Durante los primeros ciclos de desarrollo, se construyó el esqueleto de la \textbf{\textit{Single Page Application} (SPA)}, implementando el enrutamiento visual (React \cite{react} Router) y maquetando el panel de control (\textit{Dashboard}). El estado global se extrajo inmediatamente y se delegó a la librería \textbf{Zustand \cite{zustand}}, una decisión crítica en etapas tempranas que impidió que la complejidad estructural estrangulara el rendimiento al lidiar posteriormente con los flujos constantes de telemetría.

\imagen{./img/apartado_5/CapturaDashboard.png}{Panel principal de control (Dashboard) del sistema AgroSkopos}{0.95}

\subsection{Control Cinemático y Analítica Espacial}
Una vez construidos los cimientos, se integró el motor cartográfico \textbf{Leaflet \cite{leaflet}}. Se diseñaron interfaces responsivas para permitir el telemando manual direccional del vehículo a través de la web. Posteriormente, se programaron algoritmos de navegación automatizada para la generación visual de \textbf{rutas de cobertura} (como patrones agrícolas en \textit{zigzag}).

A nivel analítico espacial, la aplicación introdujo dinámicas de \textbf{\textit{Geofencing}} (delimitación poligonal de zonas seguras y parcelas) y la generación de \textbf{mapas de calor (\textit{Heatmaps})} interactivos orientados a plasmar gráficamente la densidad paramétrica sobre el terreno, como las concentraciones de humedad y el nivel de pH edafológico. Además, el panel analítico es capaz de generar de forma nativa gráficas comparativas que cruzan el histórico de estos datos, permitiendo al operador visualizar la evolución temporal de los nutrientes y la batería directamente en la interfaz de la propia aplicación sin requerir herramientas externas.

\imagen{./img/apartado_5/grafica_comparativa.png}{Gráfica comparativa de evolución temporal generada de forma nativa por la aplicación}{0.85}

\subsection{Misiones Autónomas e Internacionalización}
Con las lógicas de movimiento e interfaz estabilizadas, se diseñó el flujo operativo para dar soporte al ciclo completo de \textbf{Misiones Autónomas}. Los usuarios pueden planificar sobre un lienzo cartográfico, gestionar en tablas y poner en ejecución distintas misiones agrícolas que operan bajo una máquina de estados visual.

\imagen{./img/apartado_5/estados_mision.png}{Máquina de estados del ciclo de vida de una Misión}{0.7}

Por último, se implementó la capa de soporte multi-idioma (i18n) a través del \textit{framework} \textbf{i18next \cite{i18next}}, y se migró todo el cliente bajo los estándares de las \textbf{Aplicaciones Web Progresivas (PWA)}, habilitando el uso del portal como una aplicación nativa instalable capaz de cachear los mapas para ofrecer cargas casi instantáneas.

\section{\textit{Testing}, calidad de código y despliegue}

\subsection{Estrategia Integral de Pruebas}
Para certificar la fiabilidad y robustez técnica de un sistema distribuido como AgroSkopos, se integró una cobertura analítica exhaustiva abordando cada capa crítica de su ecosistema:

\begin{enumerate}
    \item \textbf{Pruebas Unitarias y de Componentes (\textit{Frontend}):} Apoyándose en el corredor de pruebas \textbf{Vitest \cite{vitest}} y en la biblioteca \textbf{\textit{React \cite{react} Testing Library}}, se verificó el correcto montaje y re-renderizado de la interfaz. Se aislaron los componentes complejos utilizando simulaciones exhaustivas (\textit{Mocks}) para validar la accesibilidad, las integraciones asíncronas de la API y las mutaciones persistentes en el gestor de estado global (Zustand \cite{zustand}).
    \item \textbf{Pruebas Unitarias lógicas (\textit{Backend}):} En el seno del servidor, el \textit{framework} \textbf{Jest \cite{jest}} permitió orquestar comprobaciones sobre los controladores y servicios lógicos de forma aséptica. Mediante el \textit{mocking} inyectado, se desacoplaron las dependencias reales aislando la conexión a PostgreSQL \cite{postgresql} o a las pasarelas criptográficas para garantizar un rendimiento óptimo de las pruebas sin dependencias externas.
    \item \textbf{Pruebas \textit{End-to-End} (E2E) e Integración:} Representando el nivel superior de calidad en el servidor, se integró \textbf{Testcontainers \cite{testcontainers}}. Esta herramienta orquesta contenedores efímeros de Docker \cite{docker} para instanciar bases de datos PostgreSQL \cite{postgresql} desechables exclusivas para el entorno de testeo. Esto aseguró que las peticiones simuladas por \textbf{Supertest \cite{supertest}} interactuaran con un sistema vivo bajo condiciones idénticas al entorno productivo.
    \item \textbf{Pruebas de Carga (\texttt{load testing}):} Para certificar que la arquitectura de eventos del servidor tolerara altos volúmenes de telemetría sin degradación, se diseñaron \textit{scripts} asíncronos en \textbf{k6 \cite{k6}}. Esta fase consistió en la inyección agresiva y parametrizada de cientos de usuarios virtuales concurrentes contra los \textit{endpoints} críticos.
\end{enumerate}

Para gobernar este proceso, los reportes estandarizados de cobertura de ambos clientes se fusionan mediante lógicas propias y son capturados automáticamente por un flujo de \textit{GitHub Actions} \cite{githubactions}. Finalmente, dichos reportes nutren el \textbf{análisis estático de SonarCloud \cite{sonarqube}}, que actúa como \textbf{barrera técnica (\textit{Quality Gate})}, censurando y bloqueando el despliegue de cualquier confirmación que no alcance un mínimo del $80\%$ de cobertura o que introduzca agujeros de seguridad (\textit{Security Hotspots}).

Como se puede apreciar en la figura \ref{fig:img/apartado_5/imagen_sonar.png}, el panel de control de SonarCloud centraliza las métricas de calidad y confirma el paso exitoso de este riguroso \textit{Quality Gate}. La imagen evidencia una \textbf{cobertura global superior al 90\%}, lo que significa que más de nueve de cada diez líneas de código de la aplicación están siendo evaluadas automáticamente en cada prueba. Este alto nivel de cobertura garantiza una extrema fiabilidad frente a errores (\textit{bugs}), facilita enormemente la refactorización futura sin miedo a romper funcionalidades existentes y asegura la robustez del sistema en su conjunto. Además, el panel muestra la ausencia total de vulnerabilidades y un bajísimo índice de deuda técnica (puntuación \textit{A} en fiabilidad, seguridad y mantenibilidad), certificando la madurez del código base antes de su pase a los entornos de producción.

\subsection{Despliegue y Arquitectura Cloud}
Para garantizar una disponibilidad global y sin interrupciones, la plataforma completa de AgroSkopos fue orquestada y desplegada sobre un entorno productivo híbrido.

El sistema cliente (\textit{Frontend}) se encuentra hospedado en \textbf{Vercel \cite{vercel}}. Esta elección provee una \textbf{arquitectura de red de entrega de contenidos (CDN) global} altamente optimizada para construcciones de React \cite{react}, minimizando radicalmente la latencia para el operador agrícola independientemente de su localización.

Por el contrario, el procesamiento computacional pesado y el núcleo del servidor (\textit{Backend}) residen en una \textbf{infraestructura virtualizada basada en Linux} desplegada a través de \textbf{Microsoft Azure \cite{azure}}. En este nodo central se implementó un flujo automatizado de orquestación local mediante \textbf{Docker \cite{docker} Compose}. Este archivo declarativo asegura el levantamiento secuencial y estandarizado del servidor Node.js \cite{nodejs}, el \textbf{motor en memoria Redis \cite{redis}} (esencial para el gestor de colas en segundo plano) y el \textbf{clúster transaccional de PostgreSQL \cite{postgresql}}. 

La comunicación de este nodo interno con el mundo exterior fluye de manera exclusiva a través de un \textbf{proxy inverso gestionado por Nginx}. Además de balancear las rutas HTTP convencionales y la mensajería \textit{WebSocket}, este proxy absorbe la gestión y negociación de los \textbf{certificados criptográficos SSL/TLS}, garantizando que toda la telemetría operativa transite exclusivamente bajo el protocolo seguro \textbf{HTTPS}.
